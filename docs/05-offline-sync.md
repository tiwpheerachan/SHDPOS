# 05 — Offline-first และการซิงก์

## หลักคิด

หน้าร้านหยุดขายเพราะอินเทอร์เน็ตไม่ได้ ดังนั้น **IndexedDB คือแหล่งข้อมูลที่ POS ใช้ทำงาน**
Supabase คือปลายทางที่ข้อมูลไหลไปทีหลัง ไม่ใช่สิ่งที่หน้าร้านต้องรอ

## สิ่งที่ทำได้ตอนออฟไลน์

| ทำได้ | ทำไม่ได้ |
|---|---|
| ค้นหา/สแกนสินค้าจากแคช | ดูสต๊อกสาขาอื่นแบบ realtime |
| เปิดตะกร้า ให้ส่วนลด สแกน serial | โอนย้ายสินค้าข้ามสาขา |
| รับเงินสด / บันทึกบัตร-QR ไว้ก่อน | ตรวจสอบ store credit ล่าสุดของลูกค้า |
| ออกเลขที่บิล + พิมพ์สลิป | ดู dashboard ที่รวมทุกสาขา |
| เปิด–ปิดกะ, เปิดลิ้นชัก | อนุมัติจาก HQ ที่ไม่ได้อยู่หน้าร้าน |
| คืนสินค้าจากบิลที่มีในเครื่อง | ค้นบิลเก่าที่ไม่ได้แคชไว้ |

## แถบสถานะที่พนักงานเห็น

```
🟠 ออฟไลน์ — ยังขายได้ปกติ ระบบจะซิงก์ให้อัตโนมัติเมื่อเน็ตกลับมา · 14 รอซิงก์
```

เมื่อกลับมาออนไลน์

```
🔄 กำลังซิงก์...        →        ✅ ซิงก์เรียบร้อย 14/14
```

## กลไกกันบิลซ้ำ (สำคัญที่สุด)

ทุกงานที่ต้องส่งขึ้น server มี `client_uuid` ที่สร้างจากเครื่อง POS

```ts
await enqueue("create_order", clientUuid, payload);
```

ฝั่ง server `create_order(p_payload jsonb)` เช็คก่อนเสมอ:

```sql
if v_client_uuid is not null then
  select * into v_existing from orders where client_uuid = v_client_uuid;
  if found then
    return jsonb_build_object('order_id', v_existing.id,
                              'order_no', v_existing.order_no,
                              'duplicate', true);
  end if;
end if;
```

ผลคือ **retry กี่ครั้งก็ได้บิลเดียว** ไม่ว่าจะเน็ตหลุดกลางทาง, แท็บถูกปิด, หรือเครื่องดับ

## คิวงาน (`pending`)

| ฟิลด์ | ความหมาย |
|---|---|
| `op` | `create_order` / `void_order` / `create_return` / `open_shift` / `close_shift` / `cash_movement` / `audit` / `stock_count` / `create_quotation` |
| `client_uuid` | กุญแจกันซ้ำ |
| `payload` | ข้อมูลที่จะส่ง |
| `attempts` | นับจำนวนครั้งที่ลอง |
| `status` | `pending` → `syncing` → `done` / `failed` |
| `last_error` | ข้อความผิดพลาดล่าสุด |

Sync worker (`web/src/lib/offline/sync.ts`) ทำงานเมื่อ:
- เบราว์เซอร์แจ้ง `online`
- กลับมาที่แท็บ (`visibilitychange`)
- ทุก 30 วินาที
- ทันทีหลัง `enqueue()`

ครั้งละไม่เกิน 50 งาน เก็บงานที่ `done` ไว้ 200 รายการล่าสุดเพื่อการตรวจสอบ

## เลขที่บิลตอนออฟไลน์

แต่ละเครื่องมี `terminals.receipt_prefix` ของตัวเอง (`70M1`, `70M2`, …)
เลขที่รันในเครื่อง = `{prefix}-{YYMMDD}-{running}` จึงไม่มีทางชนกันแม้หลายเครื่องออฟไลน์พร้อมกัน

เมื่อซิงก์ขึ้น server, `create_order` จะออกเลขของตัวเองอีกชุดหนึ่งและตอบกลับมา
ทั้งสองเลขถูกผูกกันผ่าน `client_uuid` (สลิปที่พิมพ์ไปแล้วยังใช้อ้างอิงได้)

## Conflict ที่เป็นไปได้ และวิธีจัดการ

| สถานการณ์ | การจัดการ |
|---|---|
| ขายของที่สต๊อกจริงหมดแล้ว (สาขาอื่นขายไปตอนเราออฟไลน์) | ยอมให้บิลผ่าน แต่บันทึก `sync_conflicts` reason `stock_negative` ให้ผู้จัดการมาปรับ |
| ราคาสินค้าเปลี่ยนระหว่างออฟไลน์ | ยึดราคาที่ขายจริง (snapshot ในบิล) ไม่ย้อนแก้ |
| บิลซ้ำจาก retry | server ตอบ `duplicate: true` — ไม่สร้างใหม่ |
| กะยังไม่มีบน server | `open_shift` ถูก sync ก่อน `create_order` เสมอ (คิวเรียงตามเวลา) |
| PIN ผู้อนุมัติตรวจไม่ได้ตอนออฟไลน์ | เทียบกับ hash ที่แคชไว้ในเครื่อง + บันทึก `is_offline = true` ใน audit |

`sync_conflicts` มีหน้าจัดการในหลังบ้านให้ผู้จัดการตัดสินใจ (ยอมรับ / ปรับสต๊อก / ยกเลิกบิล)

## ข้อจำกัดที่ต้องรู้

1. **จำนวนงานค้างสูงสุด** ตั้งไว้ที่ 500 (`settings.pos.defaults.offline_max_pending`)
   เกินกว่านั้นให้เตือนผู้จัดการ — แปลว่าเน็ตมีปัญหาเรื้อรัง ไม่ใช่แค่หลุดชั่วคราว
2. **ข้อมูลในเครื่องเป็นของเครื่องนั้น** — เคลียร์ browser data = งานค้างหาย
   ดังนั้นเครื่อง POS ควรใช้เบราว์เซอร์แยกโปรไฟล์ หรือห่อด้วย Tauri
3. **แคชสินค้าต้องรีเฟรช** — `CATALOG_VERSION` ใน `repo.ts` บังคับโหลด master ใหม่เมื่อเปลี่ยน

## การทดสอบที่ควรทำก่อนขึ้นจริง

```
1. ตัดเน็ต → ขาย 10 บิล → ต่อเน็ต → ตรวจว่าขึ้น server ครบ 10 บิล ไม่ซ้ำ
2. ตัดเน็ตกลางการซิงก์ → ต่อใหม่ → ตรวจว่าไม่มีบิลซ้ำ
3. ปิดเบราว์เซอร์ตอนมีงานค้าง → เปิดใหม่ → งานต้องยังอยู่และซิงก์ต่อ
4. สองเครื่องในสาขาเดียวกันออฟไลน์พร้อมกัน → เลขบิลต้องไม่ชนกัน
5. ขายสินค้าที่สต๊อกเหลือ 1 จากสองเครื่องพร้อมกันตอนออฟไลน์ → ต้องเห็น conflict หลังซิงก์
```
